# 给 A 的技术答辩页面提纲

本稿只写可由代码和本地记录支撑的内容；真实模型、云部署、费用图表需补验收数据后制作。

1. **架构与选择**：保留React/Workers，新增一个TypeScript API，复用Supabase Auth/Postgres；一个进程同时处理HTTP和数据库任务调度，便于两人赛期交付。配图用architecture.md。不要称已验证高并发扩容。
2. **Agent决策与事实边界**：岗位分析→证据匹配→按缺口决定追问→局部建议→本地校验。模型决定内容和追问，服务端限定步骤/工具/字段；固定流程结构化动作，不宣称原生tool calling。展示真实引用和一次实际轨迹后再说效果。
3. **工程与恢复**：创建先持久化，操作幂等、owner验证、RLS、租约token防旧执行者提交、每步检查点、调用预算。说明本地SQL和故障测试通过；真实Supabase进程重启待验收。外部模型可能已计费而结果未保存，不承诺调用严格exactly-once。
4. **成本与限制**：常规3次模型调用，追问保存和校验用规则工具。用量未知保持null。普通输入价估算不等于实际扣费，尚未处理缓存分价；真实耗时/费用/资源图待测，不能用stub数据代替。用户确认是最终事实防线。

问答准备：为什么不用大框架/多Agent？当前任务阶段明确，两人交付优先可解释、可测试、能恢复；后续扩展以实测瓶颈为依据。如何避免虚构？源引用、字段/类型/before校验、数字来源约束、缺口保留和人工确认，多层防护仍不能保证语义绝无幻觉。
